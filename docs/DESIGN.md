# B站视频智能笔记生成器 — 设计方案 v1

> 目标：输入一个 B 站视频链接，输出一份**图文混排的结构化 Markdown 笔记 + 交互式思维导图**。
> 输入：`https://www.bilibili.com/video/BVxxxx`（支持分P、番剧、稍后再看）
> 输出：`output/<标题>/notes.md` + `assets/frame_*.jpg` + `mindmap.html` + `subtitle.srt`

---

## 1. 环境约束（已实测）

| 项目 | 实测值 | 对设计的影响 |
|---|---|---|
| OS | Windows 11 | 路径转义、无 fork，任务队列用线程池 |
| Python | 3.13.14 | 避开无 cp313 wheel 的老库（PaddleOCR 主包） |
| Node | 22.22.2 | 可用于前端构建 / markmap CLI |
| ffmpeg | 9.0.2 (gyan) | ✅ 已装，音视频处理零成本 |
| GPU | **无 NVIDIA** | ASR 只能 CPU 推理，必须做"时长预估 + 云端可选" |
| 磁盘 | 172 GB 可用 | 缓存按视频粒度清理，单任务上限 3 GB |

**核心结论**：CPU-only 决定了架构上必须"**先拿字幕，拿不到才转写**"，并且转写要可中断、可续跑、可换云端引擎。

## 2. 整体架构：十级流水线

```
[0] 解析 URL → bvid / cid / p 序号
        ↓
[1] 元数据 + 字幕探测（login cookie）
        ├─ 命中 CC/AI 字幕 → 直接解析为带时间戳句段  ──┐
        └─ 未命中 → 下载音频轨 → ASR 转写 ────────────┤
        ↓                                            │
[2] 下载低清视频轨（360p/480p，仅用于抽帧）            │
        ↓                                            │
[3] 场景切换检测（ffmpeg scene 滤镜）→ 候选帧          │
        ↓                                            │
[4] 候选帧四维打分（信息量/清晰度/新颖度/时长权重）      │
        ↓                                            │
[5] 关键帧 OCR → 提取 PPT 文字、代码、公式、表格        │
        ↓                                            │
[6] 时间轴对齐：句段 + OCR 文本 + 帧引用 → 语义分块     │
        ↓                                            │
[7] Map 阶段：逐块 LLM 摘要（并行）                    │
        ↓                                            │
[8] Reduce 阶段：章节归并 → 全局总结 → 知识卡片/术语表   │
        ↓                                            │
[9] 思维导图生成（markmap HTML + mermaid 文本）        │
        ↓
[10] 渲染 notes.md（图片相对路径 + 时间戳跳转链接）
```

设计原则：**每一级产出都落盘**（`data/<bvid>/`），任一级失败可单独重跑，不用从头再来。

## 3. 核心模块设计

### 3.1 获取层 `services/downloader.py`

- 用 `yt-dlp` 作为统一入口（B 站 extractor 成熟，自动处理 wbi 签名、分P、清晰度）。
- 两种模式：
  - `--skip-download` 只取元数据 + 字幕清单（速度快，先决策走哪条路）
  - `-f "bv*[height<=480]"` 下载低清视频轨，`-f ba` 单独取音频轨
- Cookie：`data/cookies.txt`（Netscape 格式），UI 提供"扫码登录 / 粘贴 SESSDATA"两种导入方式。**不入库、不上传、写进 .gitignore**。
- 产出 `meta.json`：标题、UP主、av/bv、cid、时长、发布时间、封面、分P列表、是否多P。

### 3.2 文本源层 `services/subtitle.py` + `services/transcribe.py`

**优先级策略（关键设计）**：

| 优先级 | 来源 | 成本 | 质量 |
|---|---|---|---|
| P0 | 人工 CC 字幕 | 0 | 最高（有标点、有说话人） |
| P1 | B站 AI 字幕 | 0 | 高（时间轴准，标点少） |
| P2 | 云端 ASR（可选） | ￥ | 高 |
| P3 | 本地 faster-whisper | 0 | 中高，慢 |

- 字幕解析统一成内部结构 `Segment{start, end, text, source}`。
- P1 的 AI 字幕需要**重分段**：按标点 + 停顿间隔（>0.8s）+ 长度阈值合并成句。
- 本地 ASR：`faster-whisper`，`compute_type="int8"`，默认 `small`，可在设置切 `medium`。
  - 无标点问题：用 VAD（`vad_filter=True`）切句 + 中文标点恢复（规则 + LLM 二次修）。
  - **进度可观测**：按音频分段（每 5 分钟一段）喂入，实时回报百分比，支持断点续跑。
- 时长预估：`small` 约 8~15× 实时。1 小时视频 ≈ 10 分钟，UI 必须先告知用户。

**统一输出**：`transcript.json`（句段数组）+ `subtitle.srt`（可下载）。

### 3.3 视觉层 `services/frames.py`（用户强调的"关键图片"）

**三路候选生成**：

1. **场景切换帧**：`ffmpeg -i in.mp4 -vf "select='gt(scene,0.28)',showinfo" -vsync vfr out_%05d.jpg`
   - 从 `showinfo` 的 `pts_time` 反推时间戳，零额外依赖，比 PySceneDetect 快且稳。
2. **均匀兜底**：每 12 秒一帧（防"整段静态 PPT 只切一次"的情况）。
3. **讲解峰值帧**：字幕里出现"看这里/这个图/如图所示/公式/代码"等指代词时，向后偏移 2s 抽帧。

**四维打分（0~1 归一化后加权）**：

```
score = 0.35 * 文本信息量   # OCR 字数 + 数字/公式符号密度（无文字帧≈0）
      + 0.20 * 清晰度       # 拉普拉斯方差 → log 归一化，过滤转场模糊帧
      + 0.25 * 语义相关度   # 与所在块字幕关键词的重合率（TF-IDF 余弦）
      + 0.20 * 新颖度       # 与已选帧的 pHash 汉明距离
```

- 硬规则：单块 ≤3 张、全片 ≤40 张、pHash 距离 < 8 判重、纯色帧/黑场直接丢。
- 命名即元数据：`frame_00-12-33_003.jpg`（时间戳可直接定位回原文）。
- 缩放到最长边 1280px、JPEG q=85，单张 80~150 KB，40 张合计 <5 MB，笔记可整包分享。

### 3.4 OCR 层 `services/ocr.py`

- 引擎：**RapidOCR（PP-OCRv4 ONNX）** — 有 cp313 wheel、CPU 单帧 150~400ms、中英混排支持好。
  - 备选：PaddleOCR（更准，但 Py3.13 装不上 paddlepaddle）、云 OCR（贵）。
- 后处理（决定笔记可读性）：
  - 按 y 坐标聚类成行 → 按阅读顺序排序（避免 OCR 输出错乱）
  - 去掉 UI 水印区（B 站右上角 logo 腐蚀检测）
  - 置信度 <0.6 丢弃；连续重复行（滚动字幕）去重
  - 识别为"代码块 / 公式 / 表格"的启发式：等宽字体特征、`=∑∫` 符号密度、竖线对齐 → 分别用 ``` 、$...$、md 表格包裹

### 3.5 分块知识处理 `services/chunking.py`（用户强调的"分块"）

三级结构，对应三种粒度：

```
Video ──► Chapter[]（章节，5~12 个）──► Chunk[]（知识块，30~80 个）──► Point[]（要点）
```

**一级切块（时间 + 语义双驱动）**：
- 目标块长 600~900 汉字（约 2~3 分钟），硬上限 1200 字，重叠 80 字。
- 切点打分：句末标点 +2、停顿 >1.2s +2、出现转折/序数词（"接下来/第二个/另一方面/总结一下"）+3、块长已达标 +2 → 取局部最优切点。
- 块内同时挂载：该时间窗的 OCR 文本 + 帧引用。

**二级归并（章节）**：
- 用块摘要的向量/关键词相似度 + 序数词信号做相邻合并，章节数控制在 5~12。
- 章节标题由 LLM 二次命名（不直接复用块标题）。

**三级要点**：
- 每块 3~6 条要点，强制格式 `[mm:ss] 要点内容`，可回跳视频。

**Map-Reduce 约束**：
- Map：单块 prompt 输入 = 字幕 + OCR + 帧描述，输出严格 JSON（`summary/bullets/keywords/frames_used`）。
- Reduce：按章节聚合并"去重合并同类项"，最后全局总结。
- **反幻觉硬约束**：system prompt 明确"只依据给定材料；材料没有的写 `[材料未提及]`；所有结论必须带时间戳"。

### 3.6 总结与思维导图 `services/summarize.py` + `services/mindmap.py`

**笔记正文结构**（固定骨架，保证跨视频可比）：

```markdown
# {标题}
> UP主 · 时长 · 发布日期 · [原视频](url) · 字幕来源 · 生成时间

## 一句话总结
## 核心要点（5-8 条，带时间戳）
## 知识地图（mermaid mindmap 代码块）
## 章节
### 01 章节名 `[00:00]`
- 摘要段
- 要点列表
- 关键帧：![](assets/frame_00-02-15_004.jpg)
- 画面文字：> OCR 提取的 PPT 原文
## 关键概念 / 术语表（表格：术语 | 解释 | 时间戳）
## 存疑与待验证
## 完整字幕（<details> 折叠）
```

**思维导图双格式**：
1. `mindmap.html` — 用 markmap 生成可折叠、可缩放、可导出 PNG 的交互页面（离线可用，CDN 资源本地化）。
2. md 内嵌 ` ```mermaid mindmap ` 代码块 — GitHub/Typora/Obsidian 直接渲染。
3. 节点层级：`主题 → 章节 → 要点 → 细节`，深度 ≤4，单节点 ≤20 字（超长自动摘要缩写）。

### 3.7 导出层 `services/exporter.py`

- Markdown 渲染 + 图片相对路径（保证整个目录可打包发送）。
- 附带 `notes.frontmatter.md`：带 YAML frontmatter，可直接喂给 Obsidian / Hexo。
- 可选导出：PDF（weasyprint）、docx（python-docx）、Anki 卡片（每块要点一条）。

## 4. 技术选型

| 环节 | 选型 | 理由 | 备选 |
|---|---|---|---|
| 下载 | yt-dlp | B站支持最完整，活跃维护 | bilix |
| ASR | faster-whisper (CTranslate2 int8) | CPU 上最快，无 PyTorch 依赖 | whisper.cpp / 云端 API |
| 抽帧 | ffmpeg scene filter | 零依赖，比 OpenCV 逐帧快 10× | PySceneDetect |
| 图像打分 | opencv-python-headless + imagehash | 成熟稳定 | Pillow + numpy 手写 |
| OCR | rapidocr-onnxruntime | cp313 可用、轻量、中英混排好 | PaddleOCR / 云 OCR |
| LLM | OpenAI 兼容抽象层 | 一套代码切换 DeepSeek/智谱/通义/Ollama | 各家 SDK 直连 |
| 后端 | FastAPI + Uvicorn | 异步、SSE 进度推送天然支持 | Flask |
| 任务 | ThreadPoolExecutor + SQLite 状态机 | 单机无需 Celery/Redis | RQ |
| 前端 | 原生 HTML + 少量 JS（后续可 Vue） | 零构建，降低打包复杂度 | Vue3 + Vite |
| 导图 | markmap-autoloader + mermaid | 纯前端，无需 Node 运行时 | Graphviz |
| 存储 | SQLite（任务/缓存索引） + 文件系统 | 单机够用，免部署 | — |

## 6. 数据模型（SQLite）

```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,            -- uuid
  bvid TEXT NOT NULL,
  cid INTEGER,
  title TEXT,
  status TEXT NOT NULL,           -- queued|running|paused|failed|done
  stage TEXT,                     -- download|subtitle|transcribe|frames|ocr|chunk|summarize|export
  progress REAL DEFAULT 0,
  error TEXT,
  work_dir TEXT,
  created_at INTEGER, updated_at INTEGER
);

CREATE TABLE artifacts (          -- 每级产物指纹，支持断点续跑
  task_id TEXT, stage TEXT,
  path TEXT, hash TEXT, size INTEGER, created_at INTEGER,
  PRIMARY KEY (task_id, stage)
);

CREATE TABLE chunks (             -- 分块知识库，支持跨视频检索（后期）
  task_id TEXT, chunk_id INTEGER,
  t_start REAL, t_end REAL,
  text TEXT, summary TEXT, keywords TEXT, frame_paths TEXT
);
```

## 7. API 设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/tasks` | body: `{url, options:{asr, model, max_frames, force_ocr}}` → `{task_id}` |
| GET | `/api/tasks/{id}` | 状态快照 |
| GET | `/api/tasks/{id}/events` | SSE：`{stage, progress, message}` 实时推送 |
| POST | `/api/tasks/{id}/cancel` | 取消（子进程 kill + 状态置 cancelled） |
| GET | `/api/tasks/{id}/result` | 返回 md 正文 + 图片列表 |
| GET | `/api/tasks/{id}/download?fmt=md\|zip\|pdf` | 下载 |
| GET | `/health` `/ready` | 健康检查 |
| POST | `/api/auth/cookie` | 导入 B 站 cookie（不回显） |

错误统一结构：`{code, message, detail?, request_id}`，**不返回堆栈**。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 无 GPU，1h+ 视频转写 10~30 分钟 | 体验差 | 优先字幕；分段转写 + 实时进度 + 支持暂停续跑；UI 明示预估时长 |
| B站 AI 字幕需登录（wbi 签名 + cookie） | 拿不到字幕 | cookie 导入引导 + 无 cookie 时自动降级到 ASR，不阻塞 |
| 长视频超 LLM 上下文 | 总结失败 | 分块 map-reduce + token 预算控制（每块 ≤3k，总 ≤80k） |
| LLM 幻觉/编造 | 笔记不可信 | 强制时间戳引用 + 材料缺失写 `[材料未提及]` + 低温度(0.3) |
| OCR 误识别（代码/公式） | 笔记失真 | 置信度阈值 + 原文标注"OCR识别，可能有误差" |
| 纯语音/无画面变化视频 | 抽帧无意义 | 打分后无有效帧时跳过图片段，不硬塞截图 |
| 版权/合规 | — | 仅本机处理、不二次分发、不提供批量爬取能力 |

## 9. 分发形态：给别人装的 exe（BYO Key）

这是整个方案里最容易翻车的一节——开发机上有 Python 3.13、有 ffmpeg、有网络，目标机器上什么都没有。以下决策全部为"可分发"服务。

### 9.1 打包链路

```
源码 → PyInstaller (onedir) → dist/BiliNotes/ → Inno Setup → BiliNotes_Setup_1.0.0.exe
```

- **必须 onedir 而不是 onefile**：onefile 每次启动要解压 300MB 到临时目录，冷启动 8~15 秒，且杀软误报率极高。onedir 冷启动 <2 秒。
- 体积预算：`ffmpeg.exe` 70MB + onnxruntime 40MB + opencv 60MB + ctranslate2 30MB + 其他 ≈ **280MB 解包 / 约 130MB 安装包**。ASR 模型不打包（见 9.4）。
- **不引入 PyTorch**：faster-whisper 走 CTranslate2，省掉 2GB 依赖，这是选它而非 openai-whisper 的决定性理由。
- 前端用原生 HTML/CSS/JS，零 Node 构建链——打包时只需 `add-data`，不用维护两套工具链。

### 9.2 密钥管理（核心安全要求）

- 用户在自己的机器上填 API Key → **Windows DPAPI 加密后存本地**（`ctypes` 调 `CryptProtectData`，无需 pywin32）。
- 密文与当前 Windows 账户绑定：**拷到别的电脑解不开**，即使整个 AppData 目录被打包发出去也不泄露。
- Key 全程不出现在日志、不出现在前端回显（只显示 `sk-****3f2a`）、不写入笔记产物。
- 所有出站请求走统一 `llm.py` 网关，日志只记录 `provider / model / tokens / 耗时`。

### 9.3 首启向导（First-run Wizard）

目标机器上第一次打开必须是这个流程，否则用户会看到一片报错：

```
① 选择模型供应商（下拉，7 个预设 + 自定义）
      ↓
② 粘贴 API Key → 点"测试连接"（发一条 "ping"，2s 内返回即通过）
      ↓  ✗ 失败 → 给出该供应商的具体排查提示（余额/区域/网络），允许"跳过，稍后配置"
③ 选择转写档位：tiny(快/糙) · small(默认) · medium(准/慢)  → 显示预估耗时
      ↓
④ 下载 ASR 模型（带进度条，可暂停，约 250MB）→ 也可跳过（走纯字幕模式）
      ↓
⑤ 完成 → 进入主界面
```

**降级策略（关键）**：没有 LLM Key 时软件**仍然可用**——输出"转写全文 + 关键帧 + 章节时间轴 + OCR 文字"的笔记，只是 AI 摘要段显示为待生成的占位。绝不能因为没 Key 就白屏，那等于装了个废物。

### 9.4 模型与缓存目录

```
%APPDATA%\BiliNotes\
├── config.json          # 供应商、模型名、偏好（不含 key）
├── secrets.dat          # DPAPI 加密的 key
├── models\              # whisper 模型，首次按需下载
├── cache\<bvid>\        # 视频/音频/帧中间产物，按 LRU 上限 5GB 自动清理
└── logs\
```

输出笔记默认落在 `文档\BiliNotes\`，用户可在设置里改。

### 9.5 依赖自包含清单

### 12.3 实现期发现的三个设计变更

**① ffmpeg 的 scene 检测在 PPT 类画面上不可用 → 改用感知哈希**

原方案 `select='gt(scene,0.28)'` 实测零命中。深挖发现两个滤镜是两套度量：
`scdet` 报切换帧分数 2.069/1.708，而 `select` 的 `scene` 变量几乎不动；
且 scdet 基于灰度百分比，白底 PPT 换页只有百分之几的变化。
最终改为：先抽 1fps/96px 缩略图序列，再用 pHash 汉明距离找切换点（阈值 14）。
一次解码同时得到缩略图与切换点，准确且可控。

**② 场景检测零命中会导致 ffmpeg 以 -22 退出**
纯静态讲解视频没有切换帧，ffmpeg 因"无帧写入输出"报错。这不是异常，必须 `check=False`
并回落到均匀抽帧，否则整个视觉环节会被误判为失败。

**③ 真实视频大多没有字幕轨**
实测热门视频 `subtitles` 为空。B站 AI 字幕需要登录态 cookie 才有。
这意味着 **ASR 是主路径而非兜底路径**，模型下载体验直接决定软件能不能用。
因此把 `hf-mirror.com` 设为默认下载源，并在失败时给出"手动放置模型"的可操作指引。

## 13. 二期：账号体系、批量采集与知识库

参考项目 `douyin-knowledge-vault`（用户自己的抖音工具）后做的功能对齐。

### 13.1 参考项目的做法

| 维度 | 对方实现 | 问题 |
|---|---|---|
| 外壳 | Electron（main.js + preload + renderer） | 安装包 150MB 起，需维护 Node 构建链 |
| 登录 | Playwright `launch_persistent_context` + 手动扫码 | 要打包 Chromium；反检测脚本说明这条路本身在被对抗 |
| 采集 | 页面内 `fetch` 调私有接口，游标翻页 | 依赖页面上下文，接口变动风险高 |
| 进度 | 只在命令结束时打一行 JSON | 过程中无进度，批量时体验差 |
| 界面 | 10 个视图（总览/新增/知识库/检索/流水线/技能/卡片/止损/蒸馏/设置） | 功能密度高，但对单机工具偏重 |
| 内容 | 只处理口播 + 字幕 | **不识别画面文字**，PPT 类视频价值流失 |

### 13.2 我们的取舍

**① 不用 Playwright，改走 B站官方 passport 接口**

```
POST /x/passport-login/web/qrcode/generate  → qrcode_key + 登录链接
GET  /x/passport-login/web/qrcode/poll      → 86101 未扫 / 86090 待确认 / 86038 过期 / 0 成功
```

拿到标准 cookie 后写成 Netscape 格式，**同一份文件同时服务于 yt-dlp 和字幕接口**——
这一步顺带解决了 12.3③ 提到的"AI 字幕需要登录态"问题。
收益：省掉 150MB Chromium、无额外进程、不受浏览器版本影响。

二维码本身由后端用 `qrcode` 库渲染成 PNG data URI，不经过任何在线二维码服务，登录链接不外泄。

**② 保留 FastAPI + Web，不做 Electron**

界面改成左侧导航 + 五视图，视觉和行为对齐参考项目，但外壳仍是浏览器打开 localhost。
理由：单机工具没必要为"像个原生应用"付出双倍构建成本；PyInstaller 打包后同样是双击即用。

**③ 十视图精简为五个**

`总览 / 采集收藏 / 任务队列 / 知识库 / 设置`。
参考项目的"知识卡片、知识蒸馏、止损看板、我的技能"属于其独有业务，BiliNotes 没有对应语义，
硬凑会让界面变空。真正需要的是把"从账号到笔记"这条主线做得完整。

**④ 图文识别作为差异点保留并前置**

对方的短板恰是我们的长项。界面文案直接把这点挑明（"PPT、代码、公式都能进笔记"），
不藏在设置里。

## 14. 三期：高清关键帧与文本校验

### 14.1 关键帧为什么要低清定位、高清出图

二期的做法是下载 480p 全片再抽帧，进笔记的图实际只有 **852px 宽**。
PPT 上的小字在 OCR 里糊成一团，用户看到的图也是糊的。

但直接下载 1080p 全片代价太大（1 小时约 1GB，比 480p 慢 4 倍）。
正解是把"定位"和"出图"分开：

```
低清全片（480p）  → 只用来算场景切换、打分、决定哪几个时间点值得截
        ↓ 选中的 20-40 个时间点
1080p 直链 + ffmpeg -ss 定点 seek → 每点只拉几百 KB，出原画质
```

实测数据（216 秒视频，3 张关键帧）：

| 指标 | 低清候选 | 高清重取 |
|---|---|---|
| 宽度 | 852px | **1920px** |
| 单张耗时 | — | 0.63 秒 |
| 单张体积 | 约 40KB | 200–300KB |

40 张关键帧约 25 秒、8–12MB，比下载 1080p 全片快一个数量级，画质却是原画。
高清帧还会**重新跑一次 OCR**，小字识别准确率明显提升。

实现要点：B站直链需要 `Referer` + `User-Agent` 头（走 `-headers`），
ffmpeg 对 m4s 支持 Range seek，未登录也能拿到 1080p。

### 14.2 文本校验：音画互校

B站 AI 字幕的错主要是同音字。校验的核心判据只有一条：

> **拼音完全相同、汉字不同 → 几乎必然是同音误写**

`卷机` 和 `卷积` 都是 `juanji`，`剃度` 和 `梯度` 都是 `tidu`。
这不是模型猜测，是确定性证据。

可信来源按优先级：画面 OCR（UP 主亲手打的 PPT） > 标题与简介（UP 主自己写的）。

三层过滤，全部零成本：

| 层 | 做什么 | 实测效果 |
|---|---|---|
| 规则 | 机械重复去重、连续标点合并、英文大小写统一 | "这个这个这个" → "这个" |
| 术语锚定 | 以标题/简介为准做同音比对（分块前跑） | 提前修正，避免污染分块 |
| 音画互校 | 以画面 OCR 为准做同音比对（OCR 之后跑） | 卷机→卷积、正泽→正则、过你→过拟 |

**能力边界**（必须说清楚）：
- 只抓同音，抓不到近音（`政治化` vs `正则化`，`zhì` 与 `zé` 不同）和形近错误
- 3–4 字窗口逐片比对，修正粒度也是片段级（"卷机神经→卷积神经"而非整词）
- 多个候选词时宁可不改，避免越改越错

改了什么必须让人看见：笔记里会生成「文本校验」表格，逐条列出时间、原文、修正、依据。
不提供静默修改。

近音、语病、断句交给 LLM 校对，做成手动触发的按钮，不默认消耗用户额度。

### 14.3 为什么不用 AI 生成"更好的图"

这条路走过一遍，结论是**不能用在带文字和数字的画面上**：

| 做法 | 问题 |
|---|---|
| 超分辨率放大 | 文字笔画是"猜"出来的，OCR 反而更差 |
| 文生图重画 | 数字、标签、图例会被改写 —— 笔记里的数据不可信，比图糊严重得多 |
| 读数据 → 代码重绘 | ✅ 唯一可靠路线 |

所以规划是：
- **表格**：识别 → 直接渲染成 Markdown 表格（矢量、可编辑、可搜索）
- **图表**：多模态模型只做"读数据"（输出 JSON），matplotlib 负责画
- **照片/插画**：保留高清原帧即可，不做生成式处理

### 14.4 遗留

1. 高清重取尚未做"失败回退标记"（URL 过期时静默保留低清帧，笔记里看不出来）
2. 表格重建未实现（`rapid-table` 未接入）
3. 图表重绘未实现（需先验证多模态读表准确率）
4. 长视频的分段增量处理未实现

## 15. 并行处理：两次尝试与实测

### 15.1 双轨下载（已实现，见 14.1）

低清全片只做定位，选中帧用 1080p 定点重取。这是"下载"层面的双轨。

### 15.2 并行：第一版是错的

最初的实现是「文本获取（含下载音频）∥ 视觉（含下载视频）」，两个线程各自跑完整流程。
用 216 秒视频 + 60 秒模拟转写实测：

```
[  8.5s] 并行开始：text 下载音频 ∥ frames 下载视频
[ 11.7s] 转写开始
[ 12.0s] 视频下载 42%
[ 71.7s] 转写结束
[171.7s] OCR 结束（83 张）
[185.0s] 完成
```

总耗时 **185 秒**，而串行（8 秒转写）只要 92 秒。

原因在时间线里：视频下载从 9 秒变成了 **63 秒**。两个 yt-dlp 实例同时在拉流，
互相抢带宽，反而是负优化。

### 15.3 第二版：先取小素材，再让 CPU ∥ 网络

关键认识：并行要重叠的是**不同类型的资源**，不是两个同类操作。

```
串行（很快）：拿字幕 或 下载音频轨（几 MB，2-3 秒）
        ↓
并行：
  A 转写（纯 CPU，5-8 分钟）
  B 下载视频 + 抽帧 + OCR（网络 + CPU）
```

实测同一视频同一条件：

```
[  9.7s] 音频就绪，并行开始（转写 ∥ 下载画面）
[ 69.7s] 转写结束          ← 60 秒被完整藏进视觉处理期间
[128.8s] 视觉处理完成
[139.9s] 全部完成
```

总耗时 **132–140 秒**，转写在时间线上完全不可见。

三轮对比：185s → 132s → 140s（后两次网络波动，不能当作精确的百分比收益）。

### 15.4 瓶颈已经转移

并行之后，转写不再是瓶颈，**OCR 变成最大头**：83 张候选帧吃掉 80–100 秒。

已做的缓解：候选帧只用于打分，OCR 前缩到 720px（`max_edge`），不影响最终出图质量；
候选上限从 140 降到 100。

下一步方向（未做）：
- 候选帧先做轻量"有无文字"检测，跳过纯人脸/风景帧
- 或者降低候选密度，靠场景切换质量而非数量取胜

### 15.5 开关

`parallel_pipeline`（默认开）。弱 CPU 上两个线程会互抢计算资源，
此时关掉反而更快——所以留了开关而不是写死。

`hd_frames`（默认开）控制高清重取，关掉可省约 25 秒。

### 15.6 测量方法留下的教训

- **管道缓冲会吞输出**：`python -u ... | grep` 在超时被 kill 时数据全丢，
  必须重定向到文件再读。
- **单次测量不可信**：B站 CDN 和 OCR 耗时波动都在 ±15%，
  判断优化是否有效要看时间线结构（转写是否被隐藏），而不是总秒数。

## 16. 候选帧文字预筛

### 16.1 为什么要预筛

并行之后 OCR 成了最大头（80 张候选 ≈ 80 秒）。但其中相当一部分是纯人脸、纯风景、
片头黑场、PPT 翻页的过渡白屏 —— 这些帧跑 OCR 必然得到空结果，纯浪费。

### 16.2 判据：两个信号相乘

先用轮廓计数法试过：把边缘二值化后做横向闭运算，数长宽比像文字行的矩形。
**在表格上完全失效** —— 表格的横竖线在闭运算后仍是细线段（高 2px），
按长宽比过滤全被丢掉，整张表只能数出 1 块。

改用两个统计量相乘：

```
score = min(1, 边缘密度 / 1.2%) × min(1, 拉普拉斯方差 / 800)
```

实测（400px 缩略图）：

| 画面类型 | 边缘密度 | 拉普拉斯 | 得分 |
|---|---|---|---|
| PPT 幻灯片 | 2.40% | 3039 | **1.00** |
| 表格 | 1.66% | 2133 | **1.00** |
| 人物画面 | 0.67% | 54 | **0.04** |
| 渐变背景 | 0.00% | 0.8 | **0.00** |

阈值 0.35，分离度足够。单张 4.9–8.3ms，比一次 OCR（500–1000ms）便宜两个数量级。

### 16.3 实测收益

216 秒 PV 视频，80 张候选：

```
预筛耗时 0.39s（4.9ms/张）
保留 69 张，跳过 11 张（14%）
省下 OCR 时间 ≈ 10 秒
```

这个视频是动画、细节丰富，所以跳过率偏低。真人出镜多、黑场过渡多的视频
跳过率会明显更高 —— 那才是预筛真正发挥作用的场景。

**关键设计**：被跳过的帧仍留在候选池里，只是没有 OCR 文本（打分自然低）。
它们不会因为预筛而彻底从笔记里消失，避免"算法判断失误导致丢图"。

### 16.4 兜底

纯风景视频可能一张都过不了打分阈值（`score < 0.08`），
此时按清晰度取前 3 张，保证笔记不至于没有画面。

### 16.5 开关

`parallel_pipeline` 已暴露到设置页（"处理参数 → 并行处理"），
说明文字直接写了"CPU 核心少时建议关闭"。

## 17. 按数量批量处理

### 17.1 问题

收藏夹动辄几百条。全量处理按每条 5–10 分钟算，是几十小时的任务量。
原来的交互是"勾选视频 → 导入选中"，勾 20 条要点 20 次，勾多了又跑不完。

### 17.2 方案：从最新开始，取 N 条

采集页加了「快速处理 `[20]` 条 → 从最新开始」：

```
POST /api/favorites/import-count
{ media_id, limit(1-100), skip_done: true }
```

后端从收藏夹第一页开始拉（`order=mtime`，即收藏时间倒序），
边拉边跳过已处理的，凑够 limit 条就停 —— 最多翻 10 页（200 条），
避免"整个收藏夹都处理过了"时无限翻页。

关键实现细节：**在创建任务之前判断是否达到上限**。
第一版写成"先全部创建再 `created[:limit]` 截断"，多余任务已经进了队列，
等于白跑。

### 17.3 "已处理"的判定必须跨重启

原来只查内存里的任务队列（`manager.exists_done`），软件一重启就失效，
整批收藏会被重跑一遍。

现在两处都查：
- 任务队列：本次运行内完成过的
- **知识库目录**：扫描所有 `notes.md` 的 frontmatter `source` 字段，
  提取 BV 号（`len(token) >= 12`，即 BV + 10 位）

### 17.4 让用户看见工作量

导入成功后提示：

```
已加入 20 条，跳过 3 条已处理的；共 3.2 小时素材，预计 约 58 分钟 完成
```

估算口径：每分钟视频约 0.6 倍处理时间，队列并发 2 再减半。
精度不高（取决于有无字幕、机器性能），但足以让用户意识到"别再排了"。

### 17.5 边界

| 情况 | 行为 |
|---|---|
| limit = 0 或 > 100 | 422 拒绝 |
| 未登录 | 401，提示先扫码 |
| 收藏夹空 | 返回 `message: 这个收藏夹是空的` |
| 全部已处理 | `count: 0`，前端提示"都已产出笔记" |
| 扫 10 页仍不够 | 按实际凑到的数量提交，不报错 |

## 18. 合集 / 多P 的覆盖范围

### 18.1 三种结构不能混为一谈

B站有三个容易混淆的层级，处理方式完全不同：

| 结构 | 特征 | URL |
|---|---|---|
| 单 P 视频 | 一个 BV = 一个视频 | `video/BVxxx` |
| 多 P 投稿 | 一个 BV 下分 P1/P2/P3 | `video/BVxxx?p=2` |
| UP 主合集（ugc_season） | 多个独立 BV 组成系列 | 每集各自的 `video/BVxxx` |

收藏夹收藏的是**单个视频单元**，所以默认只处理你收藏的那一个。

### 18.2 发现的两个问题

**① 多 P 视频只处理了 P1（这是 bug）**
`yt-dlp` 对多 P 视频返回 playlist，`_pick_page` 取了第 1 个 entry，
于是 `part_count` 丢失、后续 P 全被忽略。
实测测试用的 `BV1JYsd6sE4k` 其实是 4 P（中/日/英/…四个语言版本），
之前所有测试都只处理了中文版。

修复：`probe` 时记录 `len(entries)`，笔记里明确标注
「本视频共 N 个分P，本笔记仅覆盖第 1 P」。

**② 合集完全没被识别**
用户收藏了 32 集教程里的某一集，软件不知道存在其余 31 集。

修复：新增 `app/services/series.py`，走 `view` 接口读 `ugc_season`，
拿到合集标题与全部分集 BV。合集优先于多 P 判断
（合集的每一集是独立 BV，更符合"整段看完"的预期）。

### 18.3 展开入口

采集页「快速处理」旁加了 `展开合集/分P` 开关：

```
快速处理 [20] 条 [从最新开始] ☑ 展开合集/分P
```

勾选后，导入时把每个收藏项展开成完整系列，**但总数仍受 limit 约束**——
一个 37 集的合集会直接占满 20 条配额，不会因为展开而失控。

展开时每个源视频要查一次 view 接口（约 0.2 秒），所以最多展开到 `limit × 2` 个源。

坑：第一版只在外层循环判断 limit，内层一次性把整季塞进去，
导致 limit=5 时展开出 8 项。内外两层都要检查。

## 19. 封面图被浏览器拦掉（ORB）

### 19.1 现象

采集页 20 张封面全是空白灰块，但接口返回的 `cover` 字段有值，
用 curl / httpx 直接请求也是 200 + `image/jpeg`。

### 19.2 根因

Playwright 捕获到 `net::ERR_BLOCKED_BY_ORB`。

ORB（Opaque Response Blocking）是 Chromium 的安全机制：
跨源、`no-cors` 模式的请求，如果响应缺少 CORS 头，会被判定为"不透明"而拦下。
CSS `background-image` 正好属于这一类。连用户头像（`<img>`）一起被拦。

### 19.3 解法：后端代理 + 本地缩放

`GET /api/proxy/image?url=...&w=480`

- 域名白名单（`*.hdslb.com` / `*.bilibili.com` / `*.bilivideo.com`），防 SSRF
- 补 `Referer`，避免图床防盗链
- `w` 参数在本地用 PIL 缩放

**为什么不用 B站图床自带的 `@480w.jpg` 参数**：
curl 直接请求 `${url}@480w.jpg` 返回 200 / 15KB，
但 httpx 请求同一个 URL 返回 **404** —— httpx 会规范化 URL，
`@` 在它看来是 userinfo 分隔符。本地缩放不依赖任何 CDN 特性，更可靠。

效果：320KB → 19KB，20 张封面从"加载不出来"变成秒开。

### 19.4 一条经验

**图片显示不出来时，先看 `requestfailed` 的失败原因**，
不要急着怀疑防盗链。`ERR_BLOCKED_BY_ORB` 和 403 是两回事，
前者是浏览器策略，加 Referer 也没用。

## 20. "17 分钟视频跑了很久"的完整排查

用户反馈：一个 17 分钟的旅游视频，处理了十几分钟还没出结果。
实测后发现这不是"慢"，而是**三个独立的致命 bug 叠加**。

### 20.1 现场证据

任务状态停在 `frames 29% / 检测画面切换…` 15 分钟不动。诊断过程：

```
tasks API  → status=running, progress=29, stage=frames
进程 CPU 占用 → 0%（不是"在算"，是"没在算"）
子进程 → 没有 ffmpeg，没有 yt-dlp
py-spy dump → task_0 worker 处于 idle，tqdm_monitor 线程存活
models/ → 只有 2.6MB，里面躺着一个 .incomplete 文件
```

结论：任务线程已不在干活，界面却仍显示"运行中"。

### 20.2 Bug ① 模型下载：Xet 协议 401

small 模型 484MB，15 分钟只下了 2.6MB。直接跑 `snapshot_download` 才看到真错误：

```
RuntimeError: File reconstruction error: CAS Client Error:
HTTP status client error (401 Unauthorized),
domain: https://cas-server.xethub.hf.co/v2/reconstructions/...
```

新版 `huggingface_hub` 默认通过 **Xet**（CAS 对象存储）拉大文件，
而 `hf-mirror.com` 不支持该协议 → 401 → 无休止重试。

**修复**：`HF_HUB_DISABLE_XET=1`，回退到普通 HTTP 分块下载。
这一条是所有"模型下载卡住"的总根源，之前多次误判成"网络慢"。

### 20.3 Bug ② 转写根本跑不起来：PyAV 接口变更

模型下好之后，一进 `model.transcribe()` 就崩：

```
TypeError: open() got an unexpected keyword argument 'metadata_errors'
  File ".../faster_whisper/audio.py", line 46, in decode_audio
    with av.open(input_file, mode="r", metadata_errors="ignore") as container:
```

当前环境 `av 19.0.2` 已移除该参数，而 `faster-whisper 1.2.1` 仍在传它。

**修复**：不再用 PyAV 解码，改用 **ffmpeg 解成 16kHz 单声道 PCM**，
以 `np.float32` 数组喂给 `model.transcribe()`。
ffmpeg 本来就是必需依赖（抽帧、音视频合并都靠它），
自己解反而绕开了 PyAV 的版本泥潭，也不受容器格式限制。

### 20.4 Bug ③ 卡死的任务会被"复用"

`create()` 里有去重逻辑：同一 URL 且状态活跃时直接返回已有任务。
于是用户以为失败了再点一次 → 拿到那个卡住的任务 → **什么都不发生**，
界面永远停在同一个百分比。

**修复**：Task 增加 `updated_at` 心跳（每次 `emit` 刷新），
超过 600 秒无更新判定为僵死，取消它并允许新建。
转写、下载都会持续 emit，真正静默 10 分钟一定是有问题。

### 20.5 附带修正：转写耗时预估离谱 6 倍

原系数表写着 `small = 9.0`，即 17 分钟视频预估 162 分钟。
实测（i7-11370H 4核8线程，int8）：

| 档位 | 模型体积 | 17 分钟音频实测 | 实时倍率 | 中文质量 |
|---|---|---|---|---|
| tiny | 75MB | **133 秒** | 0.13x（约 8 倍速） | 差（"导游和接送服务"→"导油和内服务"） |
| base | 145MB | 见 20.6 实测 | — | 待评估 |

预估系数已按实测量级重写，并且转写过程中改用**实测速率反推剩余时间**
（每 20 秒音频算一次 elapsed/done，比固定系数可靠）。

默认档位从 `small` 降到 `base`：484MB 的下载在网络差时是灾难，
145MB 能显著提高"第一次就能跑通"的概率。想要更高质量可在设置里切。

### 20.6 B站 AI 字幕：看着有，实际拿不到

排查中最大的意外。三条路径全部验证：

| 路径 | 结果 |
|---|---|
| `yt-dlp` 默认 `extract_info(download=False)` | `subtitles` 空 dict |
| `yt-dlp` 加 `listsubtitles=True` | 能列出 `ai-zh`，但 **`url` 字段为空** |
| `player/v2` 接口（带登录 cookie） | 返回 1 条 `ai-zh`，URL 带 `auth_key` |
| 下载该 URL | 能下到，但**内容与视频无关** |

最诡异的一条：`player/v2` 连续请求 6 次，每次返回的字幕内容都不同：

```
第1次:   6条    12.2s  覆盖 1%   首句「三星叛徒巨神兵出列」
第3次:   1条    28.6s  覆盖 3%   首句「敲重点 ↓↓↓」
第4-6次: 无 URL
6 次里合格 0 次
```

还发现一个反直觉的坑：**Referer 必须是站点根路径**。
用 `https://www.bilibili.com/video/BVxxx/` 作 Referer 时，
接口会返回完整的 6 种语言列表但 `subtitle_url` 全是空串；
换成 `https://www.bilibili.com/` 才有 URL 字段。

**处置**：这条路径保留但加**覆盖率校验**——
字幕末句时间必须覆盖视频时长的 60% 以上，否则判定为无效内容，
回落到本地转写。宁可慢，也不能把别人的字幕写进你的笔记。

### 20.7 现在的真实耗时构成

17 分钟视频（i7-11370H 实测）：

| 环节 | 耗时 |
|---|---|
| 元数据探测 | 2 秒 |
| 音频下载（22MB） | 5–15 秒 |
| 视频下载 480p（46MB） | 10–30 秒 |
| 抽缩略图（1064 张） | 19 秒 |
| **转写 tiny** | **133 秒** |
| OCR（80 张候选） | 60–80 秒 |
| LLM 总结 | 30–60 秒 |

转写与视觉并行，所以墙钟时间约 **3–5 分钟**（tiny）。
换成 base 大约多 3–5 分钟。

**对比之前**：卡死 15 分钟无输出，且再点一次毫无反应。

### 20.8 反转：AI 字幕其实能拿到，只是要重试

写完 20.6 的"不可靠"结论后，跑端到端验证时意外命中：同一次调用直接拿到
**546 句、覆盖 1058s / 1064s（99%）** 的完整字幕，整个转写环节被完全跳过。

再看前面 6 次全失败的记录，结论要修正为：

> 接口返回是**概率性**的。多数请求给的是无关碎片，
> 但有一定比例会返回真正的完整字幕。

于是策略从"一次不中就放弃"改成**多试几次 + 覆盖率校验**：
最多 5 次，每次校验`字幕末句时间 / 视频时长 >= 60%`，
任意一次达标就用，全不达标才回落转写。失败只是 0.5 秒等待，代价极小；
命中一次能省掉整个转写（17 分钟视频从 2 分钟降到 0）。

### 20.9 修复后的完整验收

同一个 17 分钟视频，端到端实测：

```
[probe   5%] 越南本地大学生带我玩越南！到底有啥不一样？18 分钟
[text   15%] 查询 B站 AI 字幕…
             AI 字幕 546 句（ai-zh，覆盖至 1058s）   ← 命中
[frames 60%] 检测画面切换… 缩略图 1064 张，检出 160 处
[frames 80%] 画面素材就绪（80 张）
            并行阶段完成：文本 193 句 / 候选帧 80 张
[frames 82%] 高清重取 21 张关键帧
[summary 84%] 音画互校完成（193 句）
[export 97%] 生成思维导图与笔记…
[done  100%] 完成，用时 129s
```

**2 分 09 秒出笔记，21 张高清关键帧，7 个知识块。**

对比修复前：卡住 15 分钟无输出、再点一次毫无反应。

### 20.10 顺带修掉的笔记质量问题

验收时发现无模型（未配 API Key）的降级摘要完全不可用：
"核心要点"里塞的是整篇五千字正文。

根因：`_fallback_chunk` 用 `text.split("。")` 切句，
而**字幕文本几乎没有标点**——十几分钟的话就是一整条超长串，
切分后只有 1 句，于是"前 4 句"等于"全文"。

修复两处：

1. `_split_sentences()`：按标点切之后，**超过 80 字的长串继续按长度硬切**，
   保证任何输入都能得到可读的短句
2. 降级时不再假装能做摘要：一句话总结改为明确提示"未配置模型"，
   核心要点改为**章节时间轴**（`00:00  章节名`），至少能当目录用

结论：没有模型时不要伪造摘要。宁可给一个诚实的目录，
也不要输出一段没人读得下去的正文。

## 21. 结构化重组：从"压缩原文"到"重写笔记"

### 21.1 问题

用户看到真实笔记后的反馈，原话概括：

> 直接转录和字幕太乱了，有些对话中英文混在一起。
> 对话可以只提取关键信息，其他语言翻译成中文。
> AI 要自行分点 —— 比如旅游视频去了三个地方，
> 那三个地方里又有不同的景点、玩的方面、吃的方面。

原来的 prompt 做的是**压缩**：把一段字幕缩成 2-4 句摘要 + 几条 bullet。
产物仍然是"按时间流排列的压缩版字幕"，只是变短了，没有变**结构**。

### 21.2 关键区分：时间轴 ≠ 内容结构

| | chapters（原有） | outline（新增） |
|---|---|---|
| 依据 | 时间切片 | 内容逻辑 |
| 回答 | "第几分钟讲了什么" | "视频讲了什么" |
| 旅游视频的产物 | 00:00-02:40 大学采访 / 02:40-05:10 文庙 … | 河内 → 玩/吃；岘港 → 玩；会安 → 玩 |
| 局限 | 同一地点被切成多段；一段里可能有两个地点 | 需要模型重排，可能漏细节 |

两者**不是替代关系**：章节保留用于跳转原视频和挂截图，
outline 负责让人读懂内容。所以笔记里两节都保留，但分工明确。

### 21.3 prompt 的三条硬要求

对应反馈里的三个诉求，写进 `_OUTLINE_TMPL`：

```
【一、只留信息，丢掉对话】
寒暄、口头禅、语气词、客套、重复、无关闲聊全删。
对话只保留有信息量的部分（观点、事实、价格、建议、经验）。

【二、外语一律译成中文】
英文句子译成简体中文；地名/店名/菜品/品牌保留通用中文译名，
必要时括号附原文。不要在正文里夹杂英文句子。

【三、自己决定怎么分层，不要套模板】
先判断视频类型再决定结构：
  旅游 / 探店：一级 = 地点，二级 = 景点 / 美食 / 交通 / 住宿 / 花费
  教程 / 知识：一级 = 知识模块，二级 = 具体方法、注意点
  访谈 / 观点：一级 = 话题，二级 = 各方观点与结论
二级"有什么写什么"，没有的不要硬凑。
```

另外两条防退化约束：

- **具体性**：每条要点必须带可核对信息（名称、价格、时长、数量、路线）。
  给了正反例：「文庙：越南第一所大学，进士石碑上刻的是汉字」
  vs「参观了很有历史意义的地方」
- **不编造**：材料没有的一律不写。

### 21.4 数据结构与渲染

```python
outline = [
  {"title": "河内", "summary": "一句话",
   "groups": [{"title": "玩的", "items": ["文庙：…", "火车街：…"]},
              {"title": "吃的", "items": ["烤肉米线：一份 18 个，约 24 元"]}]},
  {"title": "岘港", ...}
]
```

渲染成：

```markdown
## 笔记
### 一、河内
> 行程第一站，主要看大学、文庙和火车街，吃的偏酸辣。
#### 玩的
- 文庙：越南第一所大学，考生考前会来祈福，进士石碑上刻的是汉字
#### 吃的
- 烤肉米线：一份 18 个，约 24 元
## 结论
- 越南大学生中文普及度比预期高
```

**章节改为纯时间轴**（`with_bullets=not note.outline`）：
有了正文结构，章节再列一遍要点等于让人读两遍同样的东西。
现在章节只留「时间 + 标题 + 截图」，当目录和证据用。

空标题/空分组的条目在解析阶段就丢弃，避免模型偶尔返回空壳污染笔记。

### 21.5 一个必须记住的教训：测试污染了用户配置

排查过程中 `smoke_api.py` 的密钥往返测试直接操作了真实的
`%APPDATA%\BiliNotes\secrets.dat`：先写入测试 Key，再删除。
结果**用户刚填好的真实 Key 被清空**。

修复：测试在任何 `create_app()` 之前把 `data_dir` / `output_dir`
指到 `.tmp_test/`，并验证了跑完后真实文件字节数不变。

推广规则：**任何会写盘的测试，必须在导入被测模块之前改配置目录**，
而不是运行中改 —— `create_app()` 里已经实例化了 SecretStore，
事后再改 `settings.data_dir` 已经晚了。

### 21.6 致命发现：AI 字幕会张冠李戴，覆盖率校验拦不住

21.5 之后跑了一次结构化笔记，输出内容是这样的：

```
## 一句话总结
越南大学生山雨薇带博主体验小米SU7并借衣送行…
### 一、试驾小米SU7前的准备
#### 车辆信息
- 山雨薇的小米SU7售价4万9800元…
```

而视频是**越南旅游**。字幕覆盖率校验显示「546 句，覆盖至 1058s」，
视频 1064s —— 时长、句数全对得上，但内容是另一个时长相近的视频。

结论：**覆盖率只能过滤时长不符的，过滤不了时长恰好相近的错误内容**。

这类错误比"慢"严重一个数量级：用户会拿一份完全无关的笔记当资料用，
而且看起来毫无破绽（结构工整、要点具体、还带时间戳）。

处置：**`use_ai_subtitle` 默认 False，彻底走本地转写**。

代价是 17 分钟视频从 157 秒变成 299 秒（多约 2.5 分钟）。
这个代价必须付 —— 笔记工具的第一属性是内容可信，不是快。

如果以后要重新启用，需要一道语义级校验（比如字幕里的实体与标题是否相关），
仅靠时间覆盖率不够。

### 21.7 prompt 收紧：一级主题要"少而粗"

第一版结构化输出把河内拆成了四个并列一级主题：

```
一、河内：免费导游组织与本地大学生
二、河内：火车街、文庙与摩托车体验
三、河内：传统手工艺与河内大教堂
四、河内：餐饮与消费
五、岘港：巴拿山乐园
```

用户的预期是「三个地方，每个地方下面再分景点、吃的」。所以 prompt 里补了一条
**带正反例的强约束**：

```
最关键的一条：一级主题的数量要少、要粗。
正确：一级「河内」→ 二级「景点」「美食」「交通」
错误：一级「河内：火车街与文庙」+ 一级「河内：餐饮与消费」+ 一级「河内：手工艺」
```

改完立刻正确：

```
1. 河内    → 景点 / 河内大教堂 / 美食与消费
2. 岘港    → 巴拿山乐园 / 城市印象
3. 会安    → 奥黛体验 / 椰子船 / 放花灯 / 交通与导航
4. 旅行实用信息 → 网络与通讯 / 物价与消费 / 语言与沟通 / 交通
```

**给 prompt 加正反例比加形容词有效得多。** "要抽象概括"这种话模型听不懂，
但给出"正确/错误"两条对照，它立刻照着做。

### 21.8 调 prompt 不能被全流程拖住

每次改 prompt 都重跑 5 分钟（下载+转写+OCR+LLM）是不可接受的。
所以写了 `tests/retry_outline.py`：从已有笔记的「完整转录」段读回字幕，
只跑分块 + 结构化重组，**30 秒看到结果**。

这个工具让 prompt 迭代从"每轮 5 分钟"变成"每轮 30 秒"，
是本轮能快速收敛分层规则的关键。

### 21.9 反转二：并行处理在真实 CPU 负载下是负优化

关掉 AI 字幕、改走本地转写后，端到端变成 342 秒。日志里的关键一行：

```
转写完成 570 句 总耗时=286.0s（加载 0.5s）音频=1064s 实时倍率=0.3x
```

同一段音频单独跑 base 只要 **112 秒（0.11x）**。也就是说并行跑 OCR 时，
转写慢了 2.5 倍。

原因很直接：转写（CTranslate2）和 OCR（onnxruntime）都是纯 CPU 密集，
同时跑就是互相抢核。4 核 8 线程也扛不住。

**之前为什么没发现**：第 15 节测并行时，转写用的是 `time.sleep(60)` 模拟的
——它不占 CPU，所以"转写被完全藏进视觉处理"这个结论是假的。
**用 sleep 模拟 CPU 任务，测出来的并行收益毫无意义。**

修正后的调度：

```
阶段一（并行）: 转写(CPU) ∥ 下载视频 + 抽帧(网络/IO)
阶段二（串行）: OCR → 补峰值帧 → 打分 → 高清重取 → LLM
```

OCR 挪到转写结束之后独占 CPU。实测：

| 调度 | 转写耗时 | 总耗时 |
|---|---|---|
| 转写 ∥ OCR | 286s | 342s |
| 转写 ∥ 下载+抽帧，OCR 后置 | 112s | **258s** |

省 84 秒（24%）。教训：**并行的前提是"资源类型不同"**——
CPU 任务要和网络/IO 任务重叠，不能和另一个 CPU 任务重叠。
